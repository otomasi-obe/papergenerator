# Fix: Chat Conversation Creation 500 (new paper → chat, tool chat / new chat buttons)

**Goal:** Stop `POST /api/papers/<id>/conversations` from returning 500 so (a) opening a new paper auto-enters chat, and (b) the "tool chat" panel and "New Chat" button work.

**Architecture:** Single backend root cause — DB column `conversations.id` is `VARCHAR(20)` but `_gen_id()` inserts a 32-char `uuid4().hex`. Every INSERT raises `psycopg2.errors.StringDataRightTruncation` → 500. Both reported symptoms funnel through `createConversation()` in the frontend.

**Tech Stack:** Flask + SQLAlchemy + PostgreSQL (peer auth via Unix socket), Vue 3 frontend.

---

## Root Cause (confirmed from logs + DB)

- `backend/tools/chat/chat.py:74` — `_gen_id()` returns `uuid.uuid4().hex` (32 chars).
- `backend/database/models.py:237` — `Conversation.id = db.Column(db.String(20), primary_key=True)`.
- Live error: `DataError: value too long for type character varying(20)` on
  `INSERT INTO conversations (... id='8dab4964ff1e42de897cdba1ee9348e6' ...)`.
- DB state: 207 existing `conversations` rows, **all 16-char IDs** (created by a legacy path). The newer `simple_chat` create endpoint has been 500ing since it shipped.
- FK columns referencing `conversations.id`, all `VARCHAR(20)`:
  `chat_messages.conversation_id`, `chat_drafts.conversation_id`,
  `project_memory.conversation_id`, `slr_jobs.conversation_id`.

## Symptom → code path

- **New paper → chat:** `PaperEditorPage.vue:807/815` `store.newPaper()` then chat opens via `chat.ts:openPaper → loadConversations → createConversation` (when none) → `POST .../conversations` → 500.
- **Tool chat panel / "New Chat" button:** `ChatTab.vue:8` `@click="createNewChat"` → `chat.ts:693 newChatForCurrentPaper → 670 createConversation` → `POST .../conversations` → 500.

## DB access note (prerequisite)

Root `/home/sirobo/papergenerator/.env` `DATABASE_URL` has a STALE TCP password — psql/psycopg2 over TCP fail with "password authentication failed". The **running app uses peer auth via Unix socket**: `ecosystem.config.cjs` and `backend/.env` set `DATABASE_URL=postgresql:///papergenerator`. Always connect with:

```python
import psycopg2
c = psycopg2.connect('postgresql:///papergenerator')   # peer auth as user sirobo
```

Do NOT use the root `.env` TCP URL for the migration.

---

## Approach: A (primary) + B (defense-in-depth). Apply BOTH.

- **A — widen the column (robust, future-proof):** `conversations.id` + 4 FK columns → `VARCHAR(36)`. Survives full 32-char UUIDs from any code path (anticipates future inserters that also use `uuid4().hex`). Requires a one-time DB migration; existing 16-char rows untouched.
- **B — normalize ID length (consistency + immediate unblock):** change `_gen_id()` to `uuid.uuid4().hex[:12]`, matching the project's 12-char ID convention (e.g. `paper_id='696229cdad79'`). Even without A this fits `VARCHAR(20)`. With A applied, B keeps IDs tidy and consistent.

Doing both means: B unblocks immediately even if the migration is deferred, and A prevents recurrence if any other module inserts a full UUID into a conversation FK.

### Task 1: Widen `conversations.id` and dependent FK columns (DB migration)

**Objective:** Allow conversation IDs up to 36 chars across the PK and all FKs.

**Files:**
- Run: ad-hoc migration script (no Alembic in this project).

**Step 1: Verify current widths (read-only)**

```bash
cd /home/sirobo/papergenerator/backend && .venv/bin/python - <<'PY'
import psycopg2
c=psycopg2.connect('postgresql:///papergenerator'); cur=c.cursor()
for t,col in [('conversations','id'),('chat_messages','conversation_id'),
              ('chat_drafts','conversation_id'),('project_memory','conversation_id'),
              ('slr_jobs','conversation_id')]:
    cur.execute("SELECT character_maximum_length FROM information_schema.columns WHERE table_name=%s AND column_name=%s",(t,col))
    print(t,col,cur.fetchone())
c.close()
PY
```
Expected: each prints `(20,)`.

**Step 2: Apply the migration (alter PK + FKs together in one transaction)**

PostgreSQL allows `ALTER COLUMN ... TYPE varchar(36)` on a PK referenced by FKs as long as every referencing column is widened in the same transaction. Order does not matter inside the transaction.

```bash
cd /home/sirobo/papergenerator/backend && .venv/bin/python - <<'PY'
import psycopg2
c=psycopg2.connect('postgresql:///papergenerator'); cur=c.cursor()
cur.execute("BEGIN")
cur.execute("ALTER TABLE conversations  ALTER COLUMN id              TYPE varchar(36)")
cur.execute("ALTER TABLE chat_messages  ALTER COLUMN conversation_id TYPE varchar(36)")
cur.execute("ALTER TABLE chat_drafts    ALTER COLUMN conversation_id TYPE varchar(36)")
cur.execute("ALTER TABLE project_memory ALTER COLUMN conversation_id TYPE varchar(36)")
cur.execute("ALTER TABLE slr_jobs       ALTER COLUMN conversation_id TYPE varchar(36)")
c.commit(); print("migration committed")
c.close()
PY
```

**Step 3: Verify**

Re-run the Step 1 script. Expected: each prints `(36,)`.

## Risks / tradeoffs / open questions
- **Stale root `.env`:** the TCP `DATABASE_URL` password is wrong. Migration MUST use the socket URL `postgresql:///papergenerator`. Consider syncing/removing the stale root `.env` entry to avoid future confusion (optional follow-up, not required for the fix).
- **Why both A and B:** B alone fixes the reported bug; A alone fixes it too. Doing both is cheap and prevents recurrence from any other code path that inserts a 32-char UUID into a conversation FK (matches the "anticipate future errors" preference).
- **VARCHAR(36) vs TEXT:** 36 covers canonical UUID-with-dashes too. TEXT would be maximally future-proof but 36 keeps the schema self-documenting; either is acceptable.
- **Legacy 16-char rows:** untouched and still valid under both 20→36 widening and the new 12-char generator.
